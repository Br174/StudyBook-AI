# StudyBook-AI — PostHog Observability Pilot Design

Date: 2026-10-01
Status: Design specification — implementation not yet authorized
MotorLab lifecycle target: LAB only
Repository: Br174/StudyBook-AI
Branch: lab/posthog-observability-pilot-01
Base: main

## 1. Goal

Introduce a minimal, fail-safe PostHog observability pilot in StudyBook-AI to validate runtime error diagnostics before any wider MotorLab rollout.

Success means:
- StudyBook-AI still starts and works normally when PostHog is unavailable or misconfigured;
- browser runtime exceptions can be observed in PostHog;
- no session replay is enabled;
- no deliberate capture of document contents, OCR text, prompts, study notes, or other user-authored content is added;
- no lifecycle promotion occurs;
- the pilot remains isolated in LAB until device/runtime verification is complete.

## 2. Why StudyBook-AI

StudyBook-AI is the lowest-risk pilot among the currently registered app projects because it has a compact React/Vite entry point and no active application PR that would conflict with this work. The integration can be attached at the root application boundary instead of touching feature logic.

Current relevant entry point:
- src/main.jsx

Current relevant package manifest:
- package.json

## 3. Scope

In scope:
- add the official PostHog browser/React packages;
- configure PostHog at the React root;
- capture unhandled browser errors and unhandled promise rejections;
- keep console-error autocapture disabled for the pilot to reduce noise;
- disable general interaction autocapture;
- keep session replay disabled;
- use Vite environment variables for the public project token and ingestion host;
- add a safe diagnostic test path or test-only verification mechanism that does not become normal user-facing behavior;
- verify build and runtime fallback behavior;
- verify at least one controlled exception reaches PostHog before marking PROJECT_ADOPTED.

Out of scope:
- session recordings;
- product analytics dashboards;
- feature flags;
- surveys;
- user identification/profile enrichment;
- capturing document text, OCR text, uploaded-file contents, AI prompts/responses, filenames, or free-form study content;
- source-map upload automation in the first pilot;
- changes to StudyBook features or UI;
- changes to other projects;
- merge to main, CANDIDATA promotion, or MADRE promotion.

## 4. PostHog configuration model

Use the current React/Vite installation pattern documented by PostHog:
- packages: posthog-js and @posthog/react;
- Vite client variables: VITE_POSTHOG_PROJECT_TOKEN and VITE_POSTHOG_HOST;
- initialization at the React root via PostHogProvider.

Pilot configuration must explicitly prefer diagnostics-only behavior:
- autocapture: false;
- disable_session_recording: true;
- capture_exceptions.capture_unhandled_errors: true;
- capture_exceptions.capture_unhandled_rejections: true;
- capture_exceptions.capture_console_errors: false.

The public PostHog project token is a client-side project token, not a server secret. It should still be supplied through deployment environment configuration rather than copied into source files.

Current PostHog project state observed before implementation:
- active project exists;
- no events have yet been ingested;
- IP anonymization is enabled;
- session recording is currently disabled.

## 5. Fail-safe behavior

Observability is optional infrastructure and must never become a runtime dependency for core StudyBook behavior.

Required guards:
- if VITE_POSTHOG_PROJECT_TOKEN or VITE_POSTHOG_HOST is missing, render StudyBook normally without PostHog;
- PostHog initialization failures must not prevent React from mounting;
- no feature may branch on PostHog availability;
- no blocking network wait may be introduced into startup;
- existing service-worker behavior remains unchanged.

## 6. Privacy and data minimization

The pilot is technical error telemetry only.

Explicitly prohibited payload additions:
- document body text;
- OCR results;
- study notes;
- AI prompts/responses;
- uploaded document contents;
- authentication credentials or API keys;
- personal identifiers deliberately supplied by StudyBook code.

Error objects may naturally include exception messages and stack traces as required for error tracking. The implementation must not enrich those events with user-authored application content.

## 7. Files likely to change during implementation

Expected:
- package.json
- package-lock.json, if present/generated by the repository's package manager
- src/main.jsx
- a small dedicated observability helper under src/lib/ or equivalent, if this keeps initialization isolated and testable
- .env.example or equivalent documentation file, only if an existing project convention supports it

Potential test-only file:
- one small automated or controlled diagnostic test helper.

Protected from modification unless hidden complexity forces a design revision:
- AppV15 feature logic
- document parsing/OCR flows
- study modes
- service-worker behavior
- Netlify/API functions
- MotorLab lifecycle state outside this LAB

If implementation discovers that protected areas must change, work stops and returns to Bruno for amended approval.

## 8. Verification plan

Before any claim of success:
1. Dependency/install verification.
2. Production build with npm run build.
3. Startup path with PostHog variables absent: app must still render.
4. Startup path with PostHog variables present: app must still render.
5. Controlled unhandled-error or unhandled-rejection test.
6. Confirm the resulting exception is visible in the connected PostHog project.
7. Confirm no session recording was enabled.
8. Confirm no general click/form autocapture was intentionally enabled.
9. Regression check for existing StudyBook startup and service-worker registration behavior.

Source maps are explicitly deferred from the first pilot. They may be proposed later as a separate approved change if stack readability is insufficient.

## 9. Rollback

Rollback is branch-local:
- remove PostHog packages;
- remove provider/helper initialization;
- remove PostHog environment variables from the pilot deployment;
- rebuild.

Because the pilot is isolated in lab/posthog-observability-pilot-01, main remains the clean baseline throughout the experiment.

## 10. Adoption rule

The pilot may be marked PROJECT_ADOPTED only after:
- build passes;
- runtime fallback passes;
- a controlled exception is actually received by PostHog;
- no protected data-capture scope is introduced;
- Bruno approves the tested result for continued use.

Successful StudyBook validation does not automatically authorize rollout to MusicLab, GeoVision, Visionflix, Cover Lab AI, or streamflix-BV. Each subsequent project receives its own MotorLab pre-change gate and LAB verification.

## 12. Decision

Chosen approach: minimal diagnostics-only React/Vite integration in one isolated StudyBook-AI LAB.

Rejected for this phase:
- instrument MusicLab or GeoVision first: higher regression surface;
- instrument every project at once: no validated pattern yet;
- create a shared cross-project observability library first: premature abstraction;
- enable session replay or broad behavioral analytics: unnecessary for the stated MotorLab diagnostic goal.
